# 13-用户服务-技术方案

> 面向开发与运维：代码风格、本地/远程流程、以及用户服务依赖的数据结构与业务用法。

---

## 1. 代码开发原则与风格

### 1.1 分层与依赖方向

严格按多模块六边形式分层：

```
controller → api → service → repository
                ↘ contract / common（共享契约与工具）
```


| 层级         | 应该做什么                            | 不应该做什么                  |
| ---------- | -------------------------------- | ----------------------- |
| controller | HTTP 映射、取 IP、写 Cookie、组装 Request | 写业务规则、直接访问 Mapper       |
| api        | 用例编排、调用多个 service、VO 映射          | 拼 SQL、持有 Servlet API    |
| service    | 领域规则、外部系统（短信/OAuth/JWT）          | 依赖 controller           |
| repository | 持久化、ID 生成、Entity↔DTO             | 发短信、签发 JWT              |
| contract   | Request/VO/枚举/API 接口             | 依赖 Spring Web / MyBatis |


新增接口推荐路径：contract 定义 → service/repository 实现能力 → api 编排 → controller 暴露。

### 1.2 编码惯例

- **Java 21** + Spring Boot 3.5；包名 `com.flydeer.structmind.`*。
- Lombok（`@Getter/@Setter/@AllArgsConstructor` 等）广泛使用；VO 优先 `record`。
- 对象映射用 **MapStruct**（api / repository 各自有 mapper）。
- 参数校验：Jakarta Validation（`@NotBlank` / `@Pattern` / `@Size` 等）；API 入口配合 `@Valid`。
- 认证不走 Spring Security Filter 链，而用 `@AuthCheck` **+** `AuthArgumentResolver` 向 `ApiRequest` 注入 `userId` / `verified` / `allUserIds`。
- 异常分层：`common.exception.{auth,business,frequency,request}`，由 `GlobalExceptionHandler` 映射 HTTP 状态（如 401 / 403 / 400 / 429 / 500）。
- 统一响应：`ApiResult<T>`，成功 `code=0`。
- 格式化：父 POM Spotless + Palantir Java Format；提交前建议 `./mvnw spotless:apply`。
- 配置类使用 `@ConfigurationProperties` + `@RefreshScope`，前缀统一在 `app.*`。
- Repository 查询选项用 bit-flag 式 `UserOptions`，避免方法爆炸。
- MyBatis：**手写 Mapper 已废弃**；表变更后用 Generator 覆盖生成 Entity / Mapper / XML。



### 1.3 用户服务相关关键类


| 区域          | 代表类型                                                                                                   |
| ----------- | ------------------------------------------------------------------------------------------------------ |
| Controller  | `AuthController` / `UserController` / `DelegateController`                                             |
| Auth 基础设施   | `AuthCheck`、`AuthArgumentResolver`、`AuthCookieUtils`                                                   |
| API         | `AuthorizationApiImpl`、`UserMangeApiImpl`、`UserDelegateApiImpl`                                        |
| Service     | `UserService`、`UserDelegateService`、`SmsVerifyService`、`OauthService`、`JwtTokenUtils`、`RateLimitUtils` |
| Persistence | `UserInfoRepository`、`UserDelegateRepository` + MBG Entity/Mapper                                      |

## 2. 本地测试与远程部署流程



### 2.1 前置条件


| 环境       | 需要                                                                          |
| -------- | --------------------------------------------------------------------------- |
| 本地一键脚本   | JDK 21、Docker（或 Colima）、Maven Wrapper（仓库自带）                                 |
| 云服务器脚本   | JDK 21、可连通的 MySQL / Redis、（可选）.env                                          |
| 单元/切片测试  | 不强制外部中间件（controller 测试 profile 用 H2，并排除 Redis 自动配置）                         |
| 基础设施连通测试 | 本机 `3306` MySQL + `6379` Redis（`InfrastructureConnectivityTests`，连不上则 skip） |




### 2.2 数据库初始化

1. 启动 MySQL（本地可用 Compose）。
2. 执行 `doc/sql/02-user-service.sql`（创建 `user_info`、`user_delegate`）。
3. 表结构变更后：

```bash
# 编辑 repository 模块 generatorJdbc.properties 指向目标库
./bash/mybatis-generate.sh
./mvnw -pl flydeer-repository -am compile
```



### 2.3 本地运行（Compose + jar）

```bash
./bash/run.sh                 # MySQL Compose + controller :8080
./bash/run.sh --with-task     # 额外启动 task :8081
./bash/run.sh stop            # 停应用，保留 Compose
./bash/run.sh down            # 停应用并 compose down
```

说明：

- 脚本会构建可执行 jar，后台运行，日志在 `bash/.run/`。
- `compose.yaml` 当前只定义 **MySQL**；Redis 需自行安装或另起容器（`application.yml` 默认连 `localhost:6379`）。
- 健康检查脚本可能探测 `/api/v1/ping`；若该探活接口未暴露，以 Actuator 为准：`GET /actuator/health`。

常用开发命令：

```bash
./mvnw clean verify
./mvnw spotless:apply
./mvnw -pl flydeer-controller -am test
```



### 2.4 远程 / 云服务器（无 Docker）

```bash
cp .env.example .env
# 编辑 MYSQL_* / REDIS_* / SERVER_PORT / 业务密钥（JWT、OAuth、短信）等

./bash/run-server.sh              # 编译并启动 controller
./bash/run-server.sh --with-task
./bash/run-server.sh --skip-build # 已有 jar
./bash/run-server.sh status
./bash/run-server.sh restart
./bash/run-server.sh stop
```

部署检查清单：

1. JDK 21 可用，`JAVA_HOME` 正确。
2. MySQL 已建库建表，账号与 `.env` 一致。
3. Redis 端口可达（即使业务暂未深度使用，启动与连通检查会依赖）。
4. 生产关闭短信 Mock：`SMS_MOCK_ENABLED=false`，并配置阿里云密钥与模板。
5. 替换 `AUTH_JWT_SECRET`；按环境配置 OAuth redirect 与 `AUTH_FRONTEND_REDIRECT`。
6. 若 HTTPS 终结在网关，评估 `AUTH_REFRESH_COOKIE_SECURE=true` 与 Cookie 域。



### 2.5 配置热刷新

见 [00-项目概要.md](./00-项目概要.md)「热更新」：`POST /actuator/refresh` 可刷新 `@RefreshScope` 配置 Bean；代码变更仍需重启进程。

## 3. 数据结构及业务用法

用户服务持久化主要依赖 **MySQL 两张表**。Redis 已接入连接配置，但短信验证码不落 Redis（走阿里云 / Mock），限流走 **Caffeine 进程内存**。

### 3.1 表 `user_info` — 用户主档

**业务定位**：一条记录 = 一个登录渠道下的一个身份。同一自然人若用手机与 Gitee 分别登录，会是两条用户（当前未做账号合并）。


| 字段                          | 类型               | 业务性质                                                                                                  |
| --------------------------- | ---------------- | ----------------------------------------------------------------------------------------------------- |
| `id`                        | BIGINT PK        | **对外用户 ID**。应用侧生成（默认从 `10000000` 起，随机步长 1–99），写入后不变；前端展示、委托 `operateId`、JWT subject 均用它。**不是** DB 自增。 |
| `channel`                   | VARCHAR(16)      | 登录渠道枚举名：`PHONE` / `GITEE` / `GITHUB`。决定注册时是否自动 verified、能否再绑手机。                                       |
| `channel_uid`               | VARCHAR(128)     | 渠道内唯一键：手机号或 OAuth 平台 uid。与 `channel` 组成唯一索引，保证「同渠道同身份只有一个账号」。                                         |
| `phone`                     | VARCHAR(32) NULL | 绑定手机。PHONE 渠道注册时等于 `channel_uid`；OAuth 渠道初始为 NULL，绑手机后写入。资料接口返回时脱敏。                                   |
| `verified`                  | TINYINT          | `1`=已校验，`0`=未校验。PHONE 注册即为 1；OAuth 绑手机成功后置 1。写入 JWT claims，影响「需已校验」类接口。                               |
| `name`                      | VARCHAR(64)      | 展示名。PHONE 注册默认可为手机号；OAuth 用平台用户名；业务更新最长按 20 字符裁剪。                                                     |
| `status`                    | TINYINT          | `1`=ACTIVE 可用，`0`=DISABLED 禁用。登录刷新、资料、委托操作前都会要求 ACTIVE。禁用后的封禁联动委托撤销尚在 TODO。                           |
| `created_at` / `updated_at` | DATETIME(3)      | 审计时间；委托列表等场景可能间接依赖更新时间语义。                                                                             |


**典型读写路径**：


| 场景       | 用法                                                                       |
| -------- | ------------------------------------------------------------------------ |
| 短信登录     | `channel=PHONE, channel_uid=phone` 查询；无则 insert（verified=1, phone=phone） |
| OAuth 登录 | 按平台 channel + uid 查询；无则 insert（verified=0, phone=null）                   |
| 绑手机      | 更新当前行 `phone` + `verified=1`；并检查同 channel 下手机号未被他人占用                     |
| 资料查询     | 按 JWT 中的 `id` 读；对外掩码 `phone`                                             |
| Token 签发 | 使用 `id` + `verified` 生成 Access claims                                    |




### 3.2 表 `user_delegate` — 代理关系

**业务定位**：代理人申请管理被代理人账号的关系表。一对用户之间最多一条关系（唯一键），状态在生命周期内流转，而不是不断插入历史行。


| 字段                          | 类型           | 业务性质                                                                |
| --------------------------- | ------------ | ------------------------------------------------------------------- |
| `id`                        | BIGINT AI PK | **内部主键**，不对外暴露；更新状态时按此 id 定位。                                       |
| `user_id`                   | BIGINT       | **代理人**（发起 / 持有管理权限的一方）。创建时 = 当前登录用户。                               |
| `granted_user_id`           | BIGINT       | **被代理人**（被申请管理的一方）。创建 的 `operateId`。                                |
| `status`                    | VARCHAR(16)  | 运行时取值：`PENDING` / `ACCEPTED` / `REVOKE`（注意与 SQL 注释 `REVOKED` 的命名差）。 |
| `created_at` / `updated_at` | DATETIME(3)  | 创建与状态变更时间；列表 VO 暴露 `updatedAt`。                                     |


索引：

- `uk_user_granted (user_id, granted_user_id)`：保证双方关系唯一，支持「撤销后再发起」时更新同一行。
- `idx_granted_user_id`：支撑「查代理我的」（以被代理人为入口）查询。

**状态与接口对应**：


| 操作             | 写入 / 查询语义                                                                                   |
| -------------- | ------------------------------------------------------------------------------------------- |
| create         | `(user_id=我, granted_user_id=对方)` → PENDING；若已是 PENDING/ACCEPTED 则直接返回；若 REVOKE 则改回 PENDING |
| accept         | 被代理人调用；查找 `(user_id=对方, granted_user_id=我)` 且 PENDING → ACCEPTED                            |
| revoke         | 按 `relation` 决定谁是 `user_id` / `granted_user_id`，非 REVOKE 状态改为 REVOKE                        |
| query MANAGING | 以我为 `user_id` 查「我代理的」                                                                       |
| query MANAGED  | 以我为 `granted_user_id` 查「代理我的」                                                               |


**与认证的衔接**：当解析级别为 `DELEGATE` 时，会把当前用户 ACCEPTED 且关系为 MANAGING 的 `granted_user_id` 填入 `ApiRequest.allUserIds`（含自己），供后续「可代理操作他人数据」的业务使用。当前用户三件套接口使用 `SELF`，尚未启用该集合。

### 3.3 会话与非表状态


| 数据            | 存放位置            | 业务性质                                                     |
| ------------- | --------------- | -------------------------------------------------------- |
| Access Token  | 客户端持有           | JWT；含 userId、verified；默认约 2h                             |
| Refresh Token | HttpOnly Cookie | JWT；用于换发；默认约 90d；登出仅清 Cookie，无服务端黑名单                     |
| OAuth state   | 授权 URL 内签名串     | 防 CSRF；校验时间窗与签名                                          |
| 短信验证码         | 阿里云侧（或 Mock）    | Mock 模式下校验策略以实现为准，联调勿假设生产一致                              |
| 限流计数          | Caffeine（进程内）   | Key 形如 `sms:phone:*`、`sms:day:ip:*`、`login:sms:*`；多实例不共享 |

## 4. 开发时注意点（实现层）

1. **Generator 覆盖**：重新生成会覆盖同名 Entity/Mapper/XML，业务扩展放在 Repository / DTO / Options，避免改生成物后被冲掉。
2. **枚举与库值**：委托状态以 Java 枚举 `REVOKE` 为准写入字符串；写原生 SQL 或报表时不要用 `REVOKED`。
3. **Cookie Path**：Refresh 仅在 `/api/v1/auth` 路径下发送，前端刷新必须打到该前缀。
4. **配置前缀**：部分 yml 键与 `@ConfigurationProperties` 前缀存在历史不一致；改配置后应用日志 / 实际绑定值验证，必要时依赖类内默认值。
5. **格式与测试门禁**：`./mvnw clean verify`（含 Spotless、JaCoCo 等父 POM 约定）作为提交前基线。
